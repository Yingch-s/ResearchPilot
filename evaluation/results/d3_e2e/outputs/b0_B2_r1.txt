# B2 · b0 · round 1

DPR、ColBERT、ANCE、RocketQA 各自报告了怎样的资源需求（算力、索引体积的定性描述）？

---

下面按“训练/推理算力”和“索引体积”两个维度，对 DPR、ColBERT、ANCE、RocketQA 的**资源需求定性描述**做梳理。先说明：这些系统跨越 2020–2021 年前后，硬件与实现差异很大，论文中往往只给部分细节；因此以下只做**定性**归纳，并标注不确定处。

---

## 1. DPR（Dense Passage Retrieval, 2020）

**算力需求**
- 训练：需要双塔编码器（query encoder + passage encoder），在较大规模问答数据上做对比学习。典型训练使用多张 GPU（如 8×V100 级别）数天量级；相比 BM25 这类纯倒排检索，训练成本明显更高。
- 推理/检索：query 编码很轻；主要成本在**离线对全库 passage 编码**，以及在线对大规模向量做相似度搜索。
- 若用 FAISS 做近似最近邻，还需要额外的索引训练/构建算力。

**索引体积**
- 每个 passage 存一个稠密向量。以常见设置为例：向量维度 768，若用 float32，则每条 passage 约 3 KB；千万级 passage 就是几十 GB 量级。
- 相比倒排索引，DPR 索引**体积大得多**，且通常需要 FAISS/HNSW 等向量索引结构，内存占用也高。
- 若做产品量化/压缩，体积可下降，但会有精度损失。

**定性总结**：训练算力中等偏高；索引体积显著大于传统倒排，属于“稠密向量索引”路线。

---

## 2. ColBERT（2020）

**算力需求**
- 训练：同样需要双塔式编码，但 ColBERT 使用 token 级 late interaction，训练时对 batch 内 token 交互做 MaxSim，计算量比 DPR 的双塔点积更重。
- 推理/检索：
  - 离线编码：需要对每个 passage 的每个 token 生成向量，编码成本高于 DPR 的“每 passage 一个向量”。
  - 在线检索：late interaction 需要对 query token 与候选 passage token 做 MaxSim，计算量大于单向量点积；但 ColBERT 通过“先粗排再精排”或专用索引来缓解。
- 总体算力需求通常被认为**高于 DPR**，尤其在线打分阶段。

**索引体积**
- 每个 passage 存的是**多个 token 级向量**，而不是一个向量。比如 passage 长度 128 token，就约 128 个向量；即使降维到 128 维，体积仍远大于 DPR。
- 原始 ColBERT 索引体积可达 DPR 的**一个数量级以上**；后续 ColBERTv2 通过残差压缩、聚类等大幅降低，但原始版本资源需求很高。
- 因此 ColBERT 的索引体积和内存占用是其早期落地的主要瓶颈之一。

**定性总结**：训练与在线打分算力偏高；索引体积很大，原始版本尤其明显。

---

## 3. ANCE（Approximate Nearest Neighbor Negative Contrastive Learning, 2020/2021）

**算力需求**
- 训练：核心是用“近似最近邻负样本”做对比学习。它需要**周期性刷新负样本索引**，因此训练过程中要反复对全库或部分库做编码和 ANN 检索。
- 这带来显著的额外算力：不仅训练模型，还要维护/更新负样本索引；通常需要多 GPU 和大规模异步/分布式流程。
- 推理：与 DPR 类似，query 编码 + ANN 检索；在线成本取决于索引类型。
- 总体训练算力通常被认为**高于 DPR**，因为负样本挖掘本身很贵。

**索引体积**
- ANCE 本身通常沿用 DPR 式双塔 + 单向量表示，因此**索引体积与 DPR 同量级**：每条 passage 一个稠密向量。
- 但它需要额外维护用于负采样的索引，可能有多份索引或频繁重建，带来额外存储/内存开销。
- 若使用 FAISS 等 ANN 结构，内存占用同样较高。

**定性总结**：索引体积与 DPR 相近；训练算力更高，主要贵在负样本挖掘与索引刷新。

---

## 4. RocketQA（2021）

**算力需求**
- 训练：RocketQA 强调“跨批次负样本”“去噪负样本”“数据增强”等，训练流程比朴素 DPR 更复杂。它通常需要大规模 GPU 训练，并涉及多阶段（retriever + reranker）训练。
- 推理/检索：检索器仍是双塔 + ANN；但 RocketQA 常配套 cross-encoder reranker，若在线使用 reranker，则**在线算力显著增加**，因为 cross-encoder 要对 query-passage 对逐一打分。
- 若只部署 retriever，在线成本与 DPR 类似；若部署完整 pipeline，则整体算力需求更高。

**索引体积**
- 检索器部分若采用双塔单向量，索引体积与 DPR 同量级。
- 但 RocketQA 的完整系统可能包含多个模型/多份索引（如不同 retriever、reranker 不建索引但占显存/内存），整体存储与内存需求更高。
- 论文中通常不强调索引压缩，因此可认为其检索索引体积与 DPR 类方法相近，没有数量级下降。

**定性总结**：检索索引体积与 DPR 相近；训练和完整在线 pipeline 算力偏高，尤其引入 reranker 后。

---

## 横向对比（定性）

| 系统 | 训练算力 | 在线检索算力 | 索引体积 |
|---|---|---|---|
| DPR | 中等偏高 | 低（单向量点积 + ANN） | 大（单向量/ passage） |
| ColBERT | 高 | 较高（token 级 MaxSim） | 很大（多向量/ passage），原始版尤甚 |
| ANCE | 高（负样本挖掘+索引刷新） | 低-中（同 DPR 类） | 大（同 DPR 量级，另有负样本索引开销） |
| RocketQA | 高（多阶段、去噪、增强） | 中-高（若含 reranker 则高） | 大（检索索引同 DPR 量级，整体系统更大） |

---

## 需要说明的不确定点

1. **具体 GPU 数量、训练时长、索引 GB 数**：这些论文的细节在不同版本、不同复现中差异很大，上述只做定性，不宜当作精确数字。
2. **ColBERTv2 与原始 ColBERT**：资源需求差别很大；若问题指原始 ColBERT，则索引体积和算力压力更突出。
3. **RocketQA 的部署形态**：只算 retriever 还是含 reranker，资源需求差别很大；上表按“完整 pipeline 可能更贵”处理。
4. **ANCE 的索引刷新频率**：不同实现差异大，训练算力波动明显。
5. **是否使用量化/压缩**：DPR、ANCE、RocketQA 若做 PQ/OPQ 等压缩，索引体积可显著下降；ColBERTv2 也有压缩，但原始版本没有。
