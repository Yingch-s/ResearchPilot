# B2 · b0 · round 2

DPR、ColBERT、ANCE、RocketQA 各自报告了怎样的资源需求（算力、索引体积的定性描述）？

---

下面按“训练/推理算力”和“索引体积”两个维度，对 DPR、ColBERT、ANCE、RocketQA 的**资源需求定性描述**做梳理。先说明：这些系统在不同论文/版本、不同 backbone、不同语料规模下差异很大；以下主要是各论文及后续常见复现中反映出的**相对量级**，不是统一基准下的精确数字。若某点我没有足够把握，会直接标注不确定。

## 1. DPR（Dense Passage Retriever）

**算力需求**
- 训练：相对“轻量级”的双塔稠密检索方案。典型做法是用 BERT-base 作为 query encoder 和 passage encoder，在 Natural Questions 等数据上做对比学习训练。
- 论文中强调用**单机多卡**即可训练，常见描述是 8×GPU 级别；相比 ColBERT 的 late interaction 和后续 ANCE 的硬负例挖掘，DPR 的训练流程较直接。
- 推理：需要对整个 passage 语料预先编码成向量，查询时只需编码 query 并做最大内积搜索。query 侧算力很小，主要成本在**离线全库编码**和 ANN 检索服务。

**索引体积**
- 每个 passage 一个稠密向量，典型维度为 768。
- 若用 float32，单向量约 3 KB；1000 万 passage 约 30 GB 量级。实际常用 FAISS 等 ANN 索引，可能加 PQ/OPQ 压缩，体积可显著下降。
- 定性：**索引体积中等偏大**，远小于 ColBERT 的多向量索引，但大于纯倒排索引。

**不确定点**
- DPR 论文中具体 GPU 型号、训练时长、索引压缩配置在不同复现中差异较大；这里只做量级描述。

## 2. ColBERT

**算力需求**
- 训练：ColBERT/ColBERTv1 使用 BERT-base 级别的 query encoder 和 document encoder，但采用 **late interaction**，每个 token 产生一个向量。训练时需处理 token-level 交互，计算和显存开销通常高于 DPR 这类单向量双塔。
- ColBERTv2 引入 residual compression 和 denoised supervision，训练/索引流程更复杂，但目标之一是降低索引体积。
- 推理：query 编码后，需要对每个 query token 与文档 token 向量做 MaxSim。若用 PLAID 等后期优化，检索效率提升明显；但原始 ColBERT 的在线打分比单向量内积重。

**索引体积**
- 这是 ColBERT 最突出的资源问题：**索引体积很大**。
- 每个文档不再是一个向量，而是每个 token 一个向量。即使只保留部分 token，向量数量也远多于文档数。
- 原始 ColBERT 索引常被描述为比单向量 DPR 索引大一个数量级以上；ColBERTv2 通过残差压缩显著减小，但仍通常大于单向量方案。
- 定性：**索引体积大**，是其主要部署瓶颈之一。

**不确定点**
- 具体“大多少倍”取决于 token 截断、维度、压缩方式、语料规模；不宜给固定倍数。

## 3. ANCE（Approximate Nearest Neighbor Negative Contrastive Estimation）

**算力需求**
- ANCE 的核心是**用当前模型从全库 ANN 中挖掘硬负例**，并异步更新索引。因此训练算力明显高于 DPR 的静态负例训练。
- 它需要：
  - 定期/异步地对全库 passage 重新编码；
  - 维护 ANN 索引；
  - 训练时不断查询该索引获取硬负例。
- 论文中通常使用多 GPU，并强调异步索引更新以缓解训练瓶颈。整体训练成本高于 DPR，可能接近或高于朴素 ColBERT 训练中的负例采样成本。
- 推理：与 DPR 类似，query 编码 + ANN 检索，在线成本不高；主要成本在训练期和索引维护。

**索引体积**
- ANCE 本身通常仍基于**单向量稠密检索**，所以索引体积与 DPR 同量级：每个 passage 一个向量。
- 若使用相同维度、相同压缩方式，索引体积与 DPR 接近。
- 定性：**索引体积中等**，与 DPR 类似；主要额外资源在训练期的索引刷新，而非索引静态体积。

**不确定点**
- ANCE 论文中不同实验设置的 GPU 数量、刷新频率、索引类型不完全统一；这里只做相对判断。

## 4. RocketQA

**算力需求**
- RocketQA 是百度提出的稠密检索训练方案，强调：
  - 跨批次负例；
  - 去噪负例；
  - 数据增强/伪标签；
  - 通常结合更强的双塔或交叉编码器蒸馏。
- 训练流程比 DPR 复杂，涉及多阶段训练、教师模型、伪标签生成等，因此**训练算力需求较高**。
- 若包含交叉编码器 reranker 或蒸馏，额外算力更大。
- 推理：若只部署双塔 retriever，在线成本与 DPR/ANCE 类似；若包含 reranker，则在线算力显著增加。

**索引体积**
- RocketQA 的 retriever 通常也是**单向量双塔**，因此索引体积与 DPR/ANCE 同量级。
- 若使用更大 backbone 或更高向量维度，索引体积会相应增大。
- 定性：**索引体积中等**，与单向量稠密检索一致；不是 ColBERT 那种多向量大索引。

**不确定点**
- RocketQA 有多个版本和工业级实现，是否包含 reranker、蒸馏、数据增强规模等会显著影响算力描述；公开论文中的具体资源数字我无法在此准确复述。

## 汇总对比（定性）

| 系统 | 训练算力 | 在线推理算力 | 索引体积 | 主要资源瓶颈 |
|---|---|---|---|---|
| DPR | 中等，8×GPU 级常见 | 低 | 中等，单向量 | 全库编码 + ANN 服务 |
| ColBERT | 中高，token 级交互 | 中高，原始版较重 | 大，多向量 | 索引体积和在线 MaxSim |
| ANCE | 高，需异步 ANN 挖负例 | 低 | 中等，单向量 | 训练期索引刷新 |
| RocketQA | 高，多阶段/蒸馏/伪标签 | 低到中，取决于 reranker | 中等，单向量 | 训练流程和教师模型 |

## 需要特别说明的不确定信息

1. **具体 GPU 数量、训练小时数、索引 GB 数**：这些在不同论文版本、复现、语料规模下差异很大，我没有把握给出统一精确值。
2. **ColBERTv2 与原始 ColBERT 的资源差异**：ColBERTv2 显著压缩索引，但具体压缩率和检索延迟取决于实现。
3. **RocketQA 的工业部署细节**：公开论文与百度内部实际系统可能不同，尤其是 reranker 和数据增强规模。
4. **ANCE 的索引刷新频率**：这是影响训练总算力的关键，但不同实验设置不同。
